# Factory vs Abstract Factory: вибір

## Вступ

Породжувальні патерни проєктування допомагають гнучко створювати об’єкти без жорсткої прив’язки до конкретних класів. Серед найпоширеніших — **Factory Method** та **Abstract Factory**. Обидва вони інкапсулюють створення об’єктів, але застосовуються у різних ситуаціях і мають різний рівень абстракції.


## Factory Method

**Factory Method** — це патерн, який визначає інтерфейс для створення об’єкта, але дозволяє підкласам вирішувати, який саме клас створювати.

### Ідея

Базовий клас містить фабричний метод, а конкретні підкласи перевизначають його, повертаючи конкретний тип об’єкта.

### Коли використовувати

* Коли клас не знає наперед, об’єкти якого типу він має створювати
* Коли потрібно делегувати створення об’єктів підкласам
* Коли система повинна бути розширюваною без зміни існуючого коду

### Приклад

Редактор документів:

* `DocumentCreator` — базовий клас
* `PdfCreator`, `WordCreator` — підкласи
* Кожен створює свій тип документа

### Переваги

* Зменшує зв’язаність
* Підтримує принцип відкритості/закритості (OCP)
* Гнучке розширення

### Недоліки

* Збільшує кількість класів
* Логіка створення розкидана по підкласах


## Abstract Factory

**Abstract Factory** — це патерн, який надає інтерфейс для створення **сімейства пов’язаних об’єктів** без зазначення їх конкретних класів.

### Ідея

Фабрика створює не один об’єкт, а групу пов’язаних об’єктів, які повинні працювати разом.

### Коли використовувати

* Коли система повинна працювати з кількома сімействами об’єктів
* Коли потрібно гарантувати сумісність об’єктів
* Коли потрібно легко перемикатися між конфігураціями

### Приклад

Кросплатформений UI:

* `GUIFactory` — абстрактна фабрика
* `WindowsFactory`, `MacFactory` — конкретні фабрики
* Створюють кнопки, меню, чекбокси відповідного стилю

### Переваги

* Гарантує сумісність об’єктів
* Приховує конкретні класи
* Легко замінювати сімейства продуктів

### Недоліки

* Складніша структура
* Важче додавати нові типи продуктів
* Більше інтерфейсів і класів


## Основні відмінності
| Критерій             | Factory Method | Abstract Factory   |
| -------------------- | -------------- | ------------------ |
| Рівень               | Один об’єкт    | Сімейство об’єктів |
| Складність           | Простий        | Складніший         |
| Розширення           | Через підкласи | Через нові фабрики |
| Сумісність продуктів | Не гарантує    | Гарантує           |
| Кількість класів     | Менше          | Більше             |


## Висновок

**Factory Method** доцільно використовувати, коли потрібно делегувати створення одного типу об’єкта підкласам та забезпечити гнучкість розширення.

**Abstract Factory** підходить для створення цілих сімейств пов’язаних об’єктів, коли важлива їх сумісність та можливість легко змінювати конфігурацію системи.

Вибір між цими патернами залежить від складності системи: для простих випадків достатньо Factory Method, а для складних — краще використовувати Abstract Factory.
